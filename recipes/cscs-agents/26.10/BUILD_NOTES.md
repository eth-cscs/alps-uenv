# Maintainer and build notes

User-facing launch and CSCS inference instructions are in [README.md](README.md). This file records implementation constraints and build findings that should survive recipe updates.

## Recipe composition

- Spack is pinned to `v1.2.2`; `spack-packages` is pinned to commit `7318c6ac1a452a5e9f433d6de81841a036114e8f` from 2026-08-21.
- The `cscs-agents/26.10` recipe uses an `agents` environment and view, GCC 14, `unify: true`, root linking, and `add_compilers: false`.
- Runtime roots are `cscs-agent-model-config`, `cscs-agent-launchers@2026.10.20`, ShellCheck, jq, yq 4, and `squashfs`. The launcher pins `opencode@2.1.0`, `oh-my-pi@18.10.3`, `prime-agent@0.10.0`, and `cscs-agent-model-config@2026.10.20`. Keeping the harnesses out of the environment specs also keeps their bare binaries out of the `link: roots` view. Earlier package versions remain in their immutable older recipes rather than being advertised by this launcher's package.
- Keep `cleanup: runtime` and keep `squashfs` explicit. Stackinator's implicit `squashfs` group is not an explicit environment root and is otherwise eligible for garbage collection before image creation.
- The podman support packages (`crun`, `catatonit`, `fuse-overlayfs`) are explicit environment roots alongside `squashfs` for the same keep-alive reason: the launcher resolves their install paths at package-install time and `--podman` fails loudly when they are missing.

## Custom packages

### `cscs-agent-launchers`

Installs `opencode-bwrap`, `omp-bwrap`, and `prime-agent-bwrap` from one `agent-bwrap.in` template. Argument parsing, XDG isolation, bind policy, SSH-agent validation, skill setup, managed-config refresh, mutable-tool bootstrap, storage supervision, and bubblewrap assembly must remain shared. Harness-specific initialization is selected from the invoked launcher name. Refresh stamps record production/Forno credential availability, never key values, so adding or removing a gateway key triggers immediate regeneration.

`content_hash()` includes the launcher template, `storage.py`, and packaged defaults. Installation rejects unresolved substitution tokens. `storage.py` requires and is always invoked through the launcher's uv-managed Python 3.13; it deliberately does not add a Spack Python runtime dependency.

Prime Agent's supervisor runs below a persistent storage-guard process rather than the foreground client. Its bubblewrap uses `--die-with-parent`, so loss of the guard kills the daemon and prevents it from writing after the guard releases the profile lease. The socket identity hashes the node boot, Slurm allocation, profile, packaged executable, project, writable roots, bind/hide policy, GPU, IPC, SSH, podman, and `PATH` settings. Management commands that do not use the socket do not start a daemon.

### `cscs-agent-model-config`

Installs static OpenCode v2, OMP, and Prime Agent production defaults, `cscs_models.py`, and the `cscs-agent-model-config` launcher as version 2026.10.20. It has no Spack Python dependency. The launcher executes the generator through uv with `UV_PYTHON_PREFERENCE=only-managed`; its template and all defaults participate in `content_hash()`.

The generator performs metadata GETs only: production and Forno model catalogues, production prices and documentation, and public Hugging Face model metadata. It never submits inference work and never writes API-key values. Production uses the Anthropic Messages route and `{env:CSCS_INFERENCE_API_KEY}`; Forno uses OpenAI Chat Completions, provider key `cscs-forno`, and `{env:CSCS_INFERENCE_API_KEY_FORNO}`. Forno has no pricing or deployment-context endpoint, so public model metadata wins and unresolved models receive a conservative 32,768-token fallback rather than disappearing from agent configuration.


### `oh-my-pi`

Packages upstream OMP 18.10.3 release binaries for ARM64 and x86-64. Spack requires a main non-expanded source, so the release `LICENSE` is the root source and the architecture-specific executable is a conditional resource.

Installation replaces literal ED3 terminal scrollback clears (`ESC[3J`) with harmless SGR resets. `content_hash()` must continue to invalidate same-version installs when this binary mutation changes.

### `crun`

OCI runtime built with a one-line carried patch (`devpts-gid.patch`): stock crun mounts `/dev/pts` with `gid=5` whenever the calling process has euid 0, and in a single-gid-mapping user namespace that gid is unmappable, so the kernel rejects the devpts mount with EINVAL and every container start fails. The patch omits `gid=5` whenever gid 5 is not covered by `/proc/self/gid_map`, which is exactly what crun's own rootless branch does. On normal hosts the stock behavior is preserved. `content_hash()` includes the patch so a patch change invalidates same-version build-cache entries. Built `--disable-systemd --disable-criu --without-*` (wasm runtimes, bindings); hard deps are `json-c`, `libseccomp`, `libcap`.

### `catatonit`

PID-1 pause process for rootless container namespaces, from the actively maintained openSUSE fork (the original opencontainers repo is gone). Single C file, no deps.

### `fuse-overlayfs`

Overlay storage mount program for podman inside the sandbox: kernel-native overlay cannot be used because the sandbox user cannot remount mounts private, and setuid `fusermount3` does not work because the node mounts `/` nosuid. As namespace root (inside the podman wrapper's user namespace) `fusermount3` is not needed. Built from the v1.18 git-tag archive (no release tarball); autotools build with `libfuse@3.2.1:`, `autoconf`, `automake`, `libtool`, `m4`.
### `opencode`

Installs OpenCode 2.1.0 from checksummed official `@opencode/cli-linux-arm64` or `@opencode/cli-linux-x64` npm archives. GitHub release assets are not required. The tag-pinned MIT license is the primary source and is installed with the binary; there are no Bun or Node build dependencies. Archive resource placement follows the existing Prime Agent convention: the npm `package` root becomes `release`, containing `bin/opencode`. Runtime auto-update is disabled.

The launcher binds packaged `opencode-service.json` read-only over the profile's `service.json`; `disabled: true` selects the upstream private server for TUI and server-backed commands. Its stdin ownership pipe closes with the foreground client, keeping server lifetime inside the storage supervisor's writer lease. `OPENCODE_CONFIG_DIR` is unset so it cannot redirect service discovery or settings to another profile. Native `cli.json` replaces the old packaged `tui.json`.

Providers use native `providers/package/settings/capabilities` fields, explicit empty variants, and the selected CSCS default for the title agent. This prevents transport-derived adaptive-thinking parameters in background requests. Forno explicitly sets `compatibility.maxTokensField = max_tokens`; production retains `systemMessageMode = system`. Outside-project access defaults to approval. V2.1.0 has no running LSP support, and v1 plugin/server APIs are incompatible.

### `prime-agent`

Packages Prime Agent 0.10.0 from upstream's architecture-specific standalone Linux archives. Keep the complete archive together under `libexec/prime-agent`: the executable discovers `prime-agent-runtime`, bundled models, MCP services, skills, themes, HTML assets, and Photon WASM relative to itself. The view-facing `bin/prime-agent` is only a wrapper. This replaces the 0.9.4 npm/source build and removes its Node.js/npm runtime and build dependencies.

The package disables version checks but not normal provider traffic. The launcher supplies `PRIME_AGENT_CODING_AGENT_DIR`, a persistent `PRIME_AGENT_SESSION_DIR`, and a persistent `PRIME_AGENT_KERNEL_VENV`; `PRIME_AGENT_INSTALL_UV=0` forces use of the launcher-managed uv rather than an upstream installer. `session-leases` and `daemon-workers` are overlaid from node-local storage because upstream ownership records contain machine-local PIDs but no host identity.

`prime-rl` is deliberately not a dependency. It is an independent distributed reinforcement-learning training stack with GPU framework, scheduler, and training dependencies, not part of the coding-agent runtime. Prime Agent already ships a `prime-intellect` skill that can guide service and prime-rl workflows.

### `cscs-agent-skills`

Packages CSCS agent skills at commit `62b583eb3407f6266198db5d22244a233741aa45` as version 2026.09.22 and adds the `refresh-cscs-models` skill. Launchers install relative links into launcher-owned skill directories and leave user-owned directories untouched. The carried `cscs-ci-frontmatter.patch` quotes the upstream `cscs-ci` description because its embedded `CSCS CI:` colon is invalid in a YAML plain scalar and Prime Agent otherwise rejects the skill.

## Launcher invariants

- VAST home is NFSv3 with `local_lock=none`. No harness SQLite WAL database, Unix socket, PID registry, or process-ownership directory may resolve there. Switching SQLite from WAL to a rollback journal is not an accepted workaround.
- A launcher profile has one distributed writer lease under its persistent data root. Lease creation uses atomic `mkdir`; metadata records hostname, boot ID, PID/start identity, and Slurm job/step. Acquire, release, and recovery hold a sibling atomic operation lease so owner validation and pathname replacement cannot race another normal lease operation. Existing leases and operation leases are never reclaimed automatically. `--recover-storage` refuses a verifiably live owner and quarantines stale state explicitly.
- `--project-local` selects `.cscs-agents/26.10/<harness>/<instance>/{config,data,cache,state}` below the canonical `--project-dir` (default: current directory); `<harness>` is `opencode-v2`, `omp`, or `prime-agent`. `--instance` defaults to `default` and requires project-local mode. Explicit XDG root flags cannot be combined with this mode. Selection occurs before profile hashing and storage supervision, so original-argument re-execution, leases, checkpoints, recovery, and Prime daemon identity all use the same instance. Home profiles are not copied or modified.
- Instance names are restricted to an initial ASCII alphanumeric followed by ASCII alphanumerics, `.`, `_`, or `-`; project-profile path components cannot be symlinks. A new `.cscs-agents/.gitignore` ignores all profile contents, using noclobber for concurrent first launches and preserving existing rules. Profiles may hold credentials: do not commit them.
- OpenCode/OMP runtime directories now include the storage profile ID, matching the existing per-profile Prime discovery isolation. Different projects and named instances can run concurrently; the same OpenCode/OMP profile still rejects a second writer. Shared uv bootstrap stays node-local, and concurrent source edits still require separate worktrees when file isolation is needed.
- OpenCode uses an absolute database path below `/dev/shm/cscs-agent-storage-<uid>`, a local XDG cache, and local bind overlays for `state/opencode/{locks,pty,latest/locks}`. Runtime overlays are cleared before restoration under the writer lease; durable state files remain directly persistent. Home/project namespaces, local-root identity, checkpoint generations, and leases all distinguish `opencode-v2` from v1, including explicit profile-root overrides. OMP pre-creates local `XDG_{DATA,STATE,CACHE}_HOME/omp`, unsets profile/config overrides that would disable XDG routing, and sets `PI_NATIVES_DIR` explicitly because upstream's native loader disagrees about whether natives belong under data or cache.
- OpenCode and OMP publish immutable, fsynced generations every 30 seconds and on clean exit. SQLite files are created and validated with `PRAGMA quick_check` on node-local storage, then copied to the persistent generation as ordinary closed files; SQLite must never open a checkpoint target on NFS. Legacy databases and their WAL journals are likewise byte-staged locally before SQLite imports them. Publication renames a complete generation before atomically replacing the `current` pointer. Keep two generations for rollback. OMP cache and runtime directories are disposable; large data directories are direct persistent symlinks under the single-writer lease.
- The checkpoint supervisor gives its child a parent-death signal and separate process group, forwards signals to that group, retains the lease until its child exits, and terminates/reaps the child before releasing after an internal failure. Prime's detached daemon guard preserves ignored `SIGHUP`; its daemon bubblewrap dies with the guard.
- The local storage root must be an owned, non-symlink directory on a non-network filesystem and is explicitly rebound writable, including when `CSCS_AGENT_LOCAL_STORAGE_DIR` overrides `/dev/shm`. Extra binds that overlap protected local storage or runtime paths are rejected, and Prime's local overlays are appended last.

Podman volatile state MUST live on `/dev/shm`, never on the home NFS filesystem, and must be shared across podman invocations. Three verified failure modes on NFS: (1) buildah creates mode-0100 scratch directories and writes into them, relying on CAP_DAC_OVERRIDE, which the kernel does not honor across NFS (mkdir EACCES during `podman build`); (2) fuse-overlayfs unmounts leave `.nfs*` silly-rename files that break container cleanup; (3) conmon exit files and crun container state under the per-invocation tmpfs `/run` vanish when the wrapper's namespace exits, so detached containers were misreported as exited and `podman exec`/`stop` failed across invocations. The wrapper therefore binds persistent `/dev/shm` directories over `/run/libpod` and `/run/crun`, keeps `TMPDIR`/`XDG_RUNTIME_DIR`/runroot under a shared `/dev/shm/podman-<uid>-state` tree, and rewrites the generated `containers.conf`/`storage.conf` runroot+tmpdir accordingly (the store database pins these at first creation, so changing them later requires wiping the graphroot). Known limitation: `podman exec` into a detached container only works from the same podman invocation's user namespace; `podman stop` works across invocations (signal path). The `--podman` sandbox root also shadows `/var/cache` and `/var/tmp` with tmpfs because rootful containers/image hardcodes those paths for its blob cache and staging.

The launcher's `--podman` mode exposes host podman through a wrapper (`files/podman.in`, installed per-user) that re-execs through `unshare --user --map-root-user --mount --propagation slave`: a fresh user namespace where the current user is root with CAP_SYS_ADMIN over a fresh mount namespace. Inside it, `/run` is a tmpfs (the sandbox `/` is read-only), `/etc/resolv.conf` is restored from a launcher copy (the host file is a symlink into `/run`), and host podman runs rootful with generated `CONTAINERS_CONF`/`CONTAINERS_STORAGE_CONF`. Rootful-in-userns maps container root to the current user, so layer extraction never needs subid ranges; images and runtime state live under `/dev/shm/podman-$(id -u)*` while only generated configuration uses the launcher data directory. Known invariants: do not combine `--podman` with `--no-gpu-devices` (needs `/dev/fuse`); the podman stack (crun/catatonit/fuse-overlayfs) must remain explicit environment roots; the wrapper's resolv.conf restore must run before podman starts.

- Keep `--ro-bind / /` before `--proc /proc`. Reversing them exposes host `/proc` inside the private PID namespace and breaks CUDA initialization.
- The project and launcher XDG roots are writable; the remaining host filesystem is read-only. `/users`, `/home`, `/root`, and sandbox `/tmp` are hidden except for explicit bind paths.
- PID and IPC namespaces are private by default. Network and `/dev` are inherited; SSH agent access is opt-in and validates socket type, ownership, permissions, and symlinks.
- OpenCode, OMP, and Prime Agent retain separate, release-versioned `*-cscs-agents-26.10` persistent profiles; OMP's application-facing XDG data/state/cache roots are node-local and checkpointed. The older persistent `*-spack` profiles are never imported or modified automatically. Packaged skills use harness-specific ownership markers so existing managed directories continue to update. Skill synchronization replaces a managed symlink when its target text changes or when the link no longer resolves; the latter self-heals links after switching between uenv images whose packaged skill paths have the same relative spelling.
- Prime Agent daemon processes run in a guard-owned bubblewrap with `--die-with-parent`; foreground clients also retain `--die-with-parent`. Each profile sets a distinct `/tmp/cscs-prime-agent-<uid>-<profile>/prime-agent-<uid>` discovery root; daemon guard PID/socket files live there, logs use the launcher state root, and every daemon-backed client is passed the matching explicit socket. PID identity includes process start time, and the socket key includes node boot and Slurm job identity.
- OMP interactive launches use `script` and Perl to remove dynamically generated ED3 sequences. The filter is disabled with `OMP_BWRAP_FILTER_ED3=0` and is skipped when either host command is unavailable.

## CSCS managed configuration

- Static production defaults are seeded only when no user alternative exists. Managed files have SHA-256 ownership sidecars.
- A launch refresh requires either a production or Forno key, an unchanged managed file, and an executable generator. It runs immediately when the set of available gateway credentials differs from the stamp, otherwise after 86,400 seconds.
- A successful refresh replaces the complete file, records its new hash, and writes only `production=0|1 forno=0|1` to the stamp. Failure preserves the file and old stamp, causing a retry on the next launch.
- When only the Forno key is present, the generator retains production models from the published snapshot but marks them credential-unavailable when choosing the default. This avoids deleting the production provider while allowing OpenCode to start on the first live Forno model.
- OpenCode management applies to `opencode.json` even when `opencode.jsonc` exists because OpenCode merges both. Generated production and Forno providers use their distinct key environment variables and API adapters.
- OMP does not manage `models.yml` when `models.yaml` exists. OMP 18 cost blocks must contain `input`, `output`, `cacheRead`, and `cacheWrite`; the generator emits all four when production pricing is available.
- Prime Agent 0.10 manages its native `models.json`, with API keys resolved by `!printenv` commands, and loads the same Anthropic production/OpenAI Forno registrations as OMP. Its managed `settings.json` selects Kimi K2.7 Code; user edits stop launcher updates. The persistent daemon holds both the writer and maintenance leases, so client launches never rewrite profile files underneath it.
- The output budget must stay capped at half the context window (`limits()` in `cscs_models.py`), and gateway-advertised `maxTokens` must never feed the generator. External report (2026-09-10): the gateway's proxy discovery advertises `maxTokens: 262144` for `moonshotai/Kimi-K2.7-Code`, equal to the full context window. An Anthropic-adapter client with OMP's Kimi-family `alwaysSendMaxTokens` quirk shipped that value as `max_tokens`, and the Anthropic Messages API enforces `input_tokens + max_tokens <= context_window`, so any non-empty prompt failed with 400. The generator reads only `id`/`created` from `/v1/models` and derives the budget from `--max-output` (32768) with the half-context cap, so this uenv's configs never saw the bogus value. Do not remove the cap or start trusting discovery `maxTokens` even if the gateway fixes the value.
- OMP launcher defaults enable quiet startup, disable update/changelog prompts, preserve resize scrollback, and select Kimi K2.7 Code, Apertus 8B, and GLM-5.2 for the default, smol, and slow roles.
- Refresh errors are intentionally quiet unless `CSCS_MODEL_REFRESH_VERBOSE=1` is set.

## Mutable uv and Python

- Shared mutable tools default to `${CSCS_AGENT_LOCAL_STORAGE_DIR:-/dev/shm/cscs-agent-storage-$(id -u)}/tools`; the uv cache defaults to its sibling `uv-cache`. They are outside per-profile storage roots so OpenCode/OMP checkpoint restore cannot clear them. Astral's versioned installer places uv under `tools/uv/<version>/`, quietly and noninteractively with `UV_INSTALL_DIR`, `UV_NO_MODIFY_PATH=1`, and the target directory temporarily first on `PATH`.
- Managed CPython and its private executable links are stored under `python/<version>/` and `python-bin/<version>/`. Different requested versions never repoint another launcher's links.
- `uv python install --default` explicitly enables the `python-install-default` preview feature and temporarily prepends the versioned `python-bin` directory to suppress both uv bootstrap warnings.
- A version-keyed atomic bootstrap directory, uv's reported version, a ready marker, and prefix validation avoid concurrent mutation and repeated install checks. The launcher rejects private links that resolve outside `UV_PYTHON_INSTALL_DIR`.
- Validate both tool and cache roots before invoking uv: they must be owned by the current user, must not be symlinks, and must pass the existing node-local filesystem check. Reject NFS and other known network filesystems, including explicit `CSCS_AGENT_TOOLS_DIR`/`CSCS_AGENT_TOOLS_CACHE_DIR` overrides. Protect both canonical paths against extra bind mounts.
- uv, managed Python, uv-installed tools, and the cache are disposable node-local state, shared across harness profiles and recreated after node cleanup. Do not migrate or delete old XDG tool trees automatically. User-installed uv tools need reinstallation on a fresh node; agent profile settings and sessions remain persistent.
- The persistent `PATH` order is packaged harness, packaged ripgrep, mutable uv/tool bin, then inherited paths. Since the mutable tool bin has no Python links, an active secondary-uenv view supplies project Python. Prime Agent's Python tool uses its separate persistent kernel venv and does not change this project interpreter rule.
- User-facing uv uses `UV_PYTHON_PREFERENCE=system`, meaning it prefers compatible interpreters inherited on `PATH`. The model generator overrides this with `only-managed`.
- Mounting another uenv without activating its view does not expose its Python on `PATH`. Multi-uenv validation used the PyTorch `default` view: Python 3.12.12, PyTorch 2.9.1, and CUDA availability all passed while the private infrastructure interpreter remained CPython 3.13.15.
